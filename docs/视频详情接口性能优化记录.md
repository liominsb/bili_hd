## 一、结论先行

通过压测定位到请求路径上的**同步 Redis 写**（播放量 INCR），将其改造为
「本地 atomic 聚合 + 定时任务批量回写」后：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| QPS（并发 100，热态） | 10,969 | **22,505** | **+105%** |
| 平均延迟 | 9.1 ms | **4.4 ms** | **-52%** |
| P50 | 9.2 ms | 4.4 ms | -52% |
| P99 | 12.4 ms | 8.0 ms | -35% |
| 最大延迟 | 27.4 ms | 30.4 ms | 持平 |
| 错误率 | 0 | 0 | — |

参照系：完全不计数时的理论上限是 22,000 QPS，**优化后距上限仅差 2.3%**，
说明异步化本身几乎没有引入额外损耗。框架极限（空 handler `/ping`）约 10 万 QPS，
是业务接口的 4~5 倍，框架不是瓶颈。

## 二、问题是怎么被发现的

### 1. 第一次压测打的是公网，数据全废

最早压的是服务器 `43.138.153.144`，得到 47 QPS / 21ms。
看起来很慢，但 `resp wait` 占了 20.8ms，其中绝大部分是**武汉到腾讯云的 RTT**。

- 教训：**公网数据混入了 15~20ms 网络延迟，本地优化 3ms 根本体现不出来。**
  公网上那 14.8 秒的长尾，本地一枪就证明是链路丢包重传，与后端无关。

### 2. 本地也照样会骗人：基线在漂移

同样配置连跑三轮，QPS 单调下降 10673 → 9341 → 8674，avg / p99 / max 三项**同时恶化**，
而且改回原配置也不恢复。这是典型的**基线漂移**。

根因：`gin.Default()` 的 Logger 每轮往控制台刷十万行日志，
PowerShell 控制台缓冲区持续累积，写 `os.Stdout` 越来越慢；
加上 `os.Stdout` 的文件锁把所有 goroutine 串行化。

- 教训：**基线漂移时，所有 A/B 对比都是假的。**
  去掉 Logger 后连跑三轮：9305 / 9246 / 9476，波动仅 ±1.3%，基线才算钉死。

## 三、压测方法论（这次踩出来的四条纪律）

1. **每轮配置至少跑 2 次，第 1 轮当预热丢弃。**
   证据：慢请求簇的数量**恰好等于并发数**（`-c 100` 就有 100 个慢请求），
   因为每个 worker 的第一次请求要新建 Redis 连接。第 2 轮连接复用后该簇消失。

2. **A/B/A 三轮交替，不要只跑 A 一次 B 一次。**
   单枪结果说服力不够，交替跑才能排除环境波动。

3. **用利特尔法则校验数据真伪**：`并发数 ≈ QPS × 平均延迟`。
   对不上就说明数据不可信。
   - 例：`/ping` 报告 24 万 QPS，但 `1000000 / 10s = 10 万`，
     而 `10万 × 1.5ms = 150 = 并发数` ✓ → 真实是 10 万，报告的 24 万是 hey 的统计异常。

4. **先做本地对照组**：本地干净 → 问题在链路；本地也复现 → 问题在代码。
   这一步直接省掉了几天的瞎调试。

其他实用点：
- `-q` 是 **per worker**，总 QPS = `q × c`。
- `-n` 会被 `N/C` 整除截断，必须是 `-c` 的整数倍。
- 先看 `Status code distribution` 再看性能，压错路径的话数字再漂亮也没用。

## 四、定位过程：减法实验

与其猜，不如一层层往下砍。每档改一处，跑两轮取热态，用差值算成本。

| 档位 | 改动 | QPS | 与上一档差值 = 该环节成本 |
|---|---|---|---|
| 基线 | 同步 INCR + 同步 GET | 10,969 | — |
| 档 1 | 注释掉同步 INCR | **22,000** | **该行占 4.6 ms/请求** |
| 参照 | 空 handler `/ping` | ~100,000 | 框架本身不是瓶颈 |

**一次 `redisClient.Incr` 吃掉了一半吞吐。**

### 为什么一次 INCR 值 4.6ms

本机 Redis 单次命令只要 0.05~0.1ms，所以这 4.6ms 不是执行时间，是**排队时间**：

1. 每个请求要 2 次 Redis 往返（GET + INCR），100 并发 = 200 个需求，
   而 `PoolSize` 只有 100 → 一半请求在等连接；
2. 所有请求 INCR 的是**同一个 key** `video:views:34`，Redis 单线程串行执行。

（顺带修正一个认知：Redis 命令执行是单线程的，**连接池不是越大越好**。
池从 20 加到 400 反而跌了 12.5%；在干净基线下从 20 加到 100 才是对的，+12%。）

## 五、方案：播放量异步化

**核心：把"写"从请求路径上挪走，功能保留。**

### 请求路径（零同步 IO）

```go
// video_service.go:117
result.ViewCount += int(addViewDelta(videoID))
```

```go
// video_service.go:75-87
type viewCounter struct {
	total   atomic.Int64 // 本进程累计，只增不清，给页面显示用
	pending atomic.Int64 // 待刷入 Redis，flush 后清零
}

var viewDelta sync.Map // videoID(uint) -> *viewCounter

func addViewDelta(videoID uint) int64 {
	v, _ := viewDelta.LoadOrStore(videoID, &viewCounter{})
	t := v.(*viewCounter)
	t.pending.Add(1)
	return t.total.Add(1)
}
```

### 后台批量回写（10 秒一次）

```go
// video_service.go:89-100
func (s *videoServiceImpl) FlushViewDelta() {
	viewDelta.Range(func(k, v any) bool {
		videoID := k.(uint)
		t := v.(*viewCounter)
		delta := t.pending.Swap(0) // 只清 pending，total 保留
		if delta > 0 {
			s.redisClient.IncrBy(context.Background(),
				"video:views:"+strconv.FormatUint(uint64(videoID), 10), delta)
		}
		return true
	})
}
```

启动位置在 `main.go:53-63`，**复用已有的 10 秒 ticker**，与 `SyncViewCounts` 同批执行，
受 `ctx.Done()` 优雅退出保护（不单独起协程，少一个定时器且不丢数据）。

### 为什么拆成两个计数器

- `total` 只增不清 → 页面数字单调递增，不会每 10 秒倒退；
- `pending` flush 后清零 → 保证同一段增量不会被重复累加进 Redis。

只用一个计数器的话：清零则显示倒退，不清零则 flush 时反复累加导致播放量虚高。

### 代价与权衡（面试常问）

| 代价 | 实际情况 | 是否可接受 |
|---|---|---|
| 展示滞后 | 播放量最多延迟 10 秒才进 Redis | ✅ 缓存本身就把 view_count 冻结 10~70 分钟，10 秒不是新增问题 |
| 重启丢数据 | 未刷出的增量（≤10 秒的量）会丢 | ✅ 播放量非金额类数据，少几百次无影响 |
| 多实例部署 | 增量分散在各进程内存 | ✅ 最终都是 `IncrBy` 原子累加到同一个 key，汇总安全 |
| 强一致需求 | 目前方案做不到 | ⚠️ 真要强一致得换消息队列落库，对播放量属于过度设计 |

### 为什么不能简单 `go redisClient.Incr(...)`

1. goroutine 数量失控（每秒 2 万个）；
2. 顺序无法保证，出问题没法排查；
3. **做不到批量合并**——异步化的精髓是"合并 + 批量"（2 万次 INCR 合并成一次 `IncrBy 20000`），
   直接 `go` 一下做不到这点。

## 六、踩过的坑（按严重性排序）

### 1. 为修显示瑕疵，把同步 IO 请回了请求路径 ❌

曾改成 `result.ViewCount, _ = strconv.Atoi(redis.Get(...).Val())`，四宗罪：

- 又把同步网络往返加回请求路径 → QPS 从 22000 跌回 ~11000，**优化全废**；
- 用的是 `=` 不是 `+=` → 覆盖而非累加，播放量显示成极小值；
- key 不存在时 `.Val()` 返回 `""`，`Atoi("")` 报错 → **接口直接 500**
  （压测只打已存在的 key 34，所以测不出来，但线上访问新视频必崩）；
- 未检查 Redis 自身错误，Redis 异常时全体 500。

**原则：绝不为修显示层的小瑕疵，而把请求路径上的同步 IO 请回来。**

### 2. `sync.Map` 存值却断言指针 → panic

```go
LoadOrStore(videoID, viewCounter{})   // 存的是值
v.(*viewCounter)                       // 断言指针 → panic
```

两个原因必须用指针：
- 类型要配对，存 `&X` 才能断言 `*X`；`any` 擦除类型，编译器不检查，错误推迟到运行时；
- `atomic.Int64` **禁止拷贝**（`go vet copylocks` 会报），按值存等于每个 goroutine 加自己的副本，
  计数器永远是 0，flush 永远判定 `delta == 0`，**静默丢数据**。

建议：从 `any` 取东西优先用 `t, ok := v.(*T)`，失败不 panic。

### 3. 丢弃 `addViewDelta` 的返回值

写成 `addViewDelta(id); result.ViewCount += 1`，页面永远只 +1。
因为 `result` 是每次从缓存反序列化出来的新对象，`+= 1` 不会累积。
**必须接住返回值**（它返回的是本进程累计次数）。

### 4. 拿"第一枪"当基线

第一次压测普遍偏高（CPU 睿频、GC 堆小、进程刚起）。
10673 那枪后来证明是冷启动红利，热态稳态只有 9350。

## 八、功能验证（已完成 ✅）

```powershell
hey -n 100000 -c 100 -t 1 http://127.0.0.1:3000/api/v1/videos/34
```

结果：数据库 `videos.view_count`（id=34）**精确 +100,000**，零丢失、零重复。

这条数据同时证明了三段链路都通：

```
本地 atomic 聚合  →  10s 批量 IncrBy  →  Redis  →  SyncViewCounts  →  MySQL
   (请求路径)         (FlushViewDelta)              (10s 定时)         (持久化)
```

**精确相等**（不多不少）尤其关键，它排除了两类最容易犯的错：

- **少** → flush 丢数据（比如 `Swap(0)` 前值被覆盖、协程没启动）；
- **多** → 重复累加（比如 `pending` 没清零，同一段增量被反复 `IncrBy`）。

> 附带说明：这里用 `-n 100000` 固定总数，而非 `-z` 时长模式。
> 请求数精确可控，才能和数据库增量做严格对账——这也是规避 hey 在 `-z` 模式下
> 统计异常（曾把 10 万 QPS 报成 24 万）的稳妥做法。
